## 振り返り（KPT）

> Gate 3 で蒸留する。このノートの主役。

### Keep（効いた・次も続ける）
- binding の設定位置（`env.production`）を捨て設定の build で先に確かめ、生成物が空になる罠を spec に書けた。
- 戻り値を変えずメールの結果を別ログにしたことで、前ボルトの結合テストを変えずに済んだ。
- 外部サービスの仕様（宛先の条件・料金・API の形）を、型定義と公式ドキュメントで確認してから答えた。

### Problem（詰まった・摩擦・想定外）

> 各項目の先頭に分類タグ `[カテゴリ]` を付ける（棚卸しでの再発チェック集計キー）。
> カテゴリ: `spec` / `tdd` / `review` / `gate` / `boundary` / `security` / `tooling` / `other`。

- `[spec]` 前ボルトの Gate 1 で、実装の有無を確かめずに「通知設定に連動」を選択肢として勧めた。設定は未実装で、スコープの選び直しになった。
- `[review]` レビュアー 3 体を同じ作業ツリーで並行に走らせ、変異テストの一時改変を別のレビュアーが指摘として拾った。
- `[testing]` 結合側の配線（`hasRemaining`）と Owner 境界（Outbox の検索）が spec のテストケースに無く、変異テストで見つかった。
- `[gate]` 外部サービスへの実送信は、ゲートを全部通っても未確認のまま残る。

### Try（次ボルト以降でフローをこう変える）
- Gate 1 で選択肢に出す「既存機能との連動」は、その機能が実装済みかをコードで確かめてから出す。
- 変異テストをするレビュアーは、他のレビュアーが終わってから走らせるか、別の作業コピーで走らせる。
- Owner で絞る検索を足したら、別 Owner の同じキーのデータを置くテストを spec のテストケースに入れる。
